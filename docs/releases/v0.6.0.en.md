# CC Port v0.6.0 Public Beta

[中文发布说明](https://github.com/Ling-ye/cc-port/blob/main/docs/releases/v0.6.0.md)

CC Port `v0.6.0` is a substantial feature update since `v0.5.4`. The installer now includes the
standalone `cc-port.exe` CLI/MCP agent, resource repositories move to the tool-neutral Registry v1
format, Windows and WSL use independent profiles, Claude Code user instructions and auto memory
become portable resources, and Claude Skills, skills-directory Plugins, and Marketplace Plugins
follow separate native workflows.

## Downloads

- `cc-port_0.6.0_windows_x64_setup.exe`
- `SHA256SUMS.txt`

Verify the SHA-256 before running the installer. Do not download or run the internal MSI, raw desktop
executable, Desktop API sidecar, or agent executable separately. The public Release contains only the
two files above.

## Read before upgrading from v0.5.4

`v0.5.4` used Registry v7, while normal resource workflows in `v0.6.0` accept Registry v1 only.
Before upgrading, commit and push any local resource-repository changes and keep the Git history
available for recovery.

- When an old v7 repository is first connected, open **Check repository** and review the old item
  count, the number of entries rebuildable from current content, the number that will be dropped,
  and the final YAML diff.
- The one-time replacement rebuilds Registry v1 only from resource content that currently exists in
  the repository. It does not migrate old external references, platform install aliases, Plugin
  installation scopes, or other CC Port-specific metadata.
- CC Port writes nothing until you confirm. If the plan would drop a reference or setting that you
  still need, do not apply it; first recover and reorganize that information from Git history and
  the existing configuration.
- `~/.claude/plugins` is now treated as Claude Marketplace/cache runtime state for observation only,
  not as uploadable Plugin source content. Rescan each Claude profile after upgrading and review
  every Plugin's distribution and source.

## Changes

### AI invocation and local approval

- The Windows installer now contains the desktop client, Desktop API sidecar, and standalone
  `cc-port.exe` CLI/MCP agent. End users still do not need Python, Node.js, or Rust.
- In **Settings → AI automation**, you can review an enable plan for an exact native Windows profile.
  After approval, CC Port installs only its packaged `cc-port` Skill and adds a local
  `cc-port.exe mcp --stdio` entry to the tool's native configuration. It does not remove the desktop
  client or rewrite unrelated MCP servers.
- AI clients can use MCP discovery, the strict single-envelope non-interactive JSON CLI, and the
  shared `status → inventory → diff → plan → approval → apply → verify` resource workflow.
- Reads and plans may run automatically. Every write plan appears under **Pending AI approvals** and
  requires a one-time user approval. An approval is bound to the operation, `plan_hash`, and complete
  scope, expires automatically, and can be consumed only once. Target drift invalidates the old approval.

### Independent Windows and WSL profiles

- A native Windows installation and every WSL distribution have separate, stable profile ids. Codex
  and Claude Code instances are not merged merely because they share the same `tool_id`.
- Profiles explicitly store the tool, environment kind, WSL distribution, display name, and
  independent home. A stopped or unreachable WSL profile becomes unavailable and blocks writes; it
  is never treated as a missing resource or deletion request.
- The configuration, state/backup root, legacy installation target, and every profile-native target
  must remain separate from the Git resource repository and cannot contain one another.

### Claude Code Instructions, Rules, and Memory

- User-level `instruction` and Claude auto `memory` resource workflows are now available. Claude
  `CLAUDE.md` and Codex `AGENTS.md` retain their native meanings and are never auto-converted into
  one another.
- A Claude Memory is an exact Markdown directory snapshot. Every Markdown file is scanned for
  secret-like content, and ownership metadata is kept outside the content tree.
- Default project-memory slots receive opaque candidate names that do not expose a local path or
  username. Windows and WSL slots are not merged from identical content alone, and projects-layout
  downloads require a local mapping in each profile.
- Markdown under the configured Claude user `rules_dir` is discovered recursively. Only layouts
  that can be written back to the correct user scope without losing semantics are portable; other
  candidates remain read-only or blocked.

### Claude Code Skills and Plugins

- In a Claude `skills_dir`, `<name>/SKILL.md` is a plain Skill, while
  `<name>/.claude-plugin/plugin.json` identifies a `<manifest-name>@skills-dir` Plugin. A Plugin root
  and its internal `skills/*/SKILL.md` components are no longer duplicated as top-level Skills.
- A Claude Skill's command name comes from its directory. CC Port no longer imposes another tool's
  mandatory `name` or `description` frontmatter rules on native Claude Skills.
- A skills-directory Plugin is synchronized as a regular-file snapshot into the target user
  `skills_dir` or a mapped project's `.claude/skills`, with its native `<plugin>@skills-dir` enabled
  state aligned.
- A Marketplace Plugin synchronizes only a portable reference. Marketplace registration name and
  Marketplace source are stored and displayed separately. Installation uses
  `claude plugin marketplace add/install` in the target profile's own runtime and verifies the result
  through Claude's CLI.
- Upload and download validate manifest identity, component placement, custom relative paths,
  JSON/Markdown structure, links, secret-like content, and content fingerprints. CC Port does not
  execute Plugin scripts, hooks, MCP, LSP, monitors, or `bin` contents while transferring them.
- Claude `.claude-plugin/plugin.json`, JSON state, and CLI commands are never used for Codex. Codex
  `.codex-plugin/plugin.json`, TOML state, and installation workflow remain separate.

### Registry v1 and repository checks

- `registry.yaml` now contains only the tool-neutral `(kind, name)` identity and exactly one
  repository-relative `path` or external `source`. Derived metadata, local profiles, user
  directories, target paths, and runtime state do not enter the Registry.
- Optional `cc-port.yaml` stores platform/tool allowlists, install aliases, and Plugin installation
  intent; other tools do not need to understand it.
- Every remote refresh audits the Registry read-only at one commit. **Check repository** shows issues,
  default choices, and the final YAML diff. A repair commits only `registry.yaml`; it does not move,
  rewrite, or delete resource content and does not modify `cc-port.yaml`.
- A missing, malformed, linked Registry or invalid overlay fails closed for remote-dependent upload
  and installation while leaving local discovery available.

### Clearer desktop information

- Plugin rows, details, and batch plans use human-readable platforms and distributions such as
  **Claude Code · Skills-directory Plugin (@skills-dir)** and **Claude Code · Marketplace Plugin**.
- Claude Marketplace name, portable source, and version policy are edited separately. Changing the
  origin type clears locator fields that no longer apply.
- The delete dialog shows localized platform, scope, and action details instead of exposing internal
  track, scope, or method tokens.
- The Guide page now includes a restrained project-repository and GitHub Star action.

## Public Beta limitations

- The installer is not Authenticode-signed. Windows SmartScreen may show an unknown-publisher
  warning. Verify the download domain and `SHA256SUMS.txt`, then use **More info** to continue.
- Automatic updates are unavailable. Windows 10/11 x64 is the only officially distributed desktop
  platform, and Git for Windows with Git Credential Manager is still required.
- Automatic AI bootstrap currently supports native Windows profiles only. Existing WSL inventory,
  plan, and apply workflows remain available, but a Windows process is never reported as a verified
  WSL MCP connection.
- AI approval is an application-level workflow control, not operating-system-level proof of human
  presence. The AI host must still prevent an agent from modifying CC Port's local state directly or
  impersonating the desktop-sidecar channel.
- Automatic Claude Marketplace installation requires a usable Claude CLI in the target profile's own
  runtime and a portable Marketplace source. Windows and WSL CLIs cannot substitute for each other.
  Managed scope is read-only, and project/local scope requires an exact saved project mapping.
- Claude content synchronization supports manifest-backed skills-directory Plugins only. A
  manifestless `--plugin-dir` source is not treated as portable Plugin content. Project Plugins
  remain subject to Claude workspace trust and component permissions, and changes may require a
  Claude Code restart or `/reload-plugins`.
- Each Claude profile currently parses one explicit user-level `settings_path`. CC Port does not
  automatically merge managed policy, trusted project/local settings, or temporary `--settings`
  sources.
- Claude project Instructions and project Rules remain read-only. Nested user Rules remain blocked
  until they are reorganized into an explicitly portable layout. Claude auto Memory is not installable
  as a Codex resource.
- WSL LX symbolic links still block the affected resource. Windsurf and OpenCode presets remain experimental.

## Upgrade

Finish active writes, then run the `v0.6.0` installer over the existing installation. The installer
does not delete your resource repository, resources in AI tools' native directories, or CC Port's
local state, backups, and operation history. After upgrading, review the Registry v1 check before
applying it, then rescan every Windows/WSL profile. To enable AI invocation, review and approve the
corresponding native Windows profile under **Settings → AI automation**.
